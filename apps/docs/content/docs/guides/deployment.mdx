The framework's runtime is a pure `fetch` handler — it takes a `Request` and returns a `Response`. This makes it deployable to any platform that supports the Web Standards API.

## Entry shims

An entry shim connects the framework handler to your deployment platform. It imports the virtual `@sundayceo/framework/server-entry` module and wires it to the platform's request lifecycle.

<Tabs items={["Cloudflare Workers", "Hono (Node.js)", "Hono (Bun)"]}>
  <Tab value="Cloudflare Workers">
    ```ts title="entry.cloudflare.ts"
    import handler from "@sundayceo/framework/server-entry";

    export default {
      fetch: (request: Request, env: unknown, ctx: unknown) =>
        handler.fetch(request, { env, ctx }),
    };
    ```

  </Tab>
  <Tab value="Hono (Node.js)">
    ```ts title="entry.hono.ts"
    import { serve } from "@hono/node-server";
    import { Hono } from "hono";
    import handler from "@sundayceo/framework/server-entry";

    const app = new Hono();
    app.all("*", (c) => handler.fetch(c.req.raw));

    serve({ fetch: app.fetch, port: 3000 }, (info) => {
      console.log(`Listening on http://localhost:${info.port}`);
    });
    ```

  </Tab>
  <Tab value="Hono (Bun)">
    ```ts title="entry.bun.ts"
    import { Hono } from "hono";
    import handler from "@sundayceo/framework/server-entry";

    const app = new Hono();
    app.all("*", (c) => handler.fetch(c.req.raw));

    export default app;
    ```

## The server entry

`@sundayceo/framework/server-entry` is a virtual module generated by the Vite plugin. It imports your `app.ts` and `routes.gen.ts`, wires them into `createHandler`, and exports the handler:

```ts
// What the virtual module generates (conceptually):
import { createHandler } from "@sundayceo/framework";

import { app } from "./app";
import * as manifest from "./routes.gen";

export default createHandler({
	app,
	routes: manifest.routes,
	templates: manifest.templates,
	errorPages: manifest.errorPages,
	hydrationManifest: manifest.hydrationManifest,
});
```

You never write this yourself — the Vite plugin handles it.

## Platform context

The second argument to `handler.fetch` is the platform context. It's passed through to your `createApp` context factory:

```ts
// In entry shim:
handler.fetch(request, { env, ctx });

// In app.ts:
export const app = createApp<{ env: Record<string, unknown>; ctx: unknown }>({
	context: (request, platform) => ({
		db: platform?.env?.DB,
	}),
});
```

This lets you access platform-specific bindings (KV, D1, R2, etc.) in your loaders.

## Building for production

The Vite plugin runs a two-pass build:

1. **Server build** (SSR) — produces the server bundle with all route modules
2. **Client build** — produces individual bundles for each interactive slot

```bash
vite build
```

The output goes to `dist/` and includes both the server handler and client assets.

## Vite config

```ts title="vite.config.ts"
import { defineConfig } from "vite";

import { frameworkPlugin } from "@sundayceo/framework/vite";

export default defineConfig({
	plugins: [frameworkPlugin()],
});
```

The `frameworkPlugin` accepts an optional `clientBase` option for configuring the base path of client-side assets:

```ts
frameworkPlugin({ clientBase: "/assets" });
```

<Callout type="info">
	The framework works with any platform that can call a `fetch` function. If your platform can
	handle `Request → Response`, you can deploy to it.
</Callout>
